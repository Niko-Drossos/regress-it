# Model Card — Regress-It

## Model details
- **Type:** 1-D linear regression, `y = w·x + b`, fit with mini-batch SGD
  (PyTorch `nn.Linear(1, 1)`).
- **Hyperparameters:** learning rate, batch size and epoch budget come from the
  API request body; defaults are in `api/configs/default.yaml`.
- **Owner:** Nicholas Drossos — CST-435, Grand Canyon University.
- **Version:** reported live by `GET /version` (git SHA + PyTorch version).

## Intended use
- **Primary:** an interactive teaching demo showing how a linear model trains and
  how the learning rate decides whether it converges or diverges.
- **Out of scope:** any real decision-making. The model is trained on *synthetic*
  data drawn from a line the demo itself chose, so it has no external validity.

## Data
- Synthetic points from `y = slope·x + intercept + N(0, noise²)`, generated by
  `shared/data.generate_linear` and stored in the Supabase `datasets` table.
- Default dataset: slope 2.5, intercept 1.0, noise σ = 2.0, n = 500,
  x ~ Uniform[−10, 10], seed 42.

## Training and stopping
After every epoch, in order:
1. **Divergence** — the loss or a weight is non-finite, or the loss exceeds 100×
   the untrained model's loss.
2. **Plateau** — the best *training* loss has not improved by a relative
   `min_delta` (default 1e-4) for `patience` epochs (default 20).
3. **Budget** — otherwise, the epoch cap.

Early stopping watches training loss only, so the held-out split never
influences training. Each run stores which rule ended it (`status`), how many
epochs it ran, the stopping configuration, and the full per-epoch loss history.

## Metrics
- **MSE, MAE and R² on a held-out 20% test split**, computed once inside the API
  and persisted to the Supabase `runs` table. The UI displays those stored
  numbers and never recomputes them.
- Reference converged run (default dataset, lr = 0.01): test MSE ≈ 4.18,
  R² ≈ 0.980, fitted slope 2.501, fitted intercept 0.828.

## Limitations
- **Linearity is assumed.** The model will underfit any non-linear signal, and
  nothing in the metrics will flag that it is the wrong model class.
- **The intercept cannot be recovered exactly.** The generating intercept is
  1.0, but the best least-squares fit this sample admits is 0.836, and every
  converged run reproduces that. This is a limit of 500 noisy points, not a bug,
  and more training will not close the gap.
- **Error is at the noise floor, not zero.** Test MSE ≈ 4.18 against a noise
  variance of σ² = 4.0 means almost all remaining error is irreducible. R² of
  0.98 describes fit to *this* synthetic data, not predictive confidence.
- **Learning-rate sensitivity.** Stability requires `η < 1/E[x²]` ≈ 0.030 on the
  default dataset. Above it the run diverges; just below it (η = 0.03) the run
  still converges but to a visibly worse slope of 2.330.
- **Diverged runs have meaningless metrics, not absent ones.** At lr = 0.035 the
  stored MSE is ≈ 6.2 × 10⁶ and R² ≈ −29175; only when the loss overflows to
  NaN/infinity (e.g. lr = 1.5) are the metrics stored as NULL. Neither kind of
  number says anything about model quality — read the `status` column first.
  `POST /predict` refuses a diverged run with 409 for this reason.
- **No uncertainty estimate.** A prediction is returned as a single number, with
  no interval and no indication of how far the input sits from the training
  range.

## Ethical considerations
A non-technical client must be told these limits plainly. The demo is built so
the limits are visible rather than buried: the Train tab draws the true
generating line next to the fitted one instead of showing only the fit, diverged
runs are stored and labelled rather than quietly dropped, and predictions are
refused outright on a run whose weights are not a model. Reporting R² = 0.98
without the surrounding context would be technically true and materially
misleading.

## What we log (and what we do not)
- Logged: run hyperparameters, stopping configuration, metrics, fitted weights,
  per-epoch loss history, and every served prediction as `(run_id, x, yhat)`.
- Not logged: any personal data. The dataset is synthetic by construction, and
  the service collects nothing about the person using it.
